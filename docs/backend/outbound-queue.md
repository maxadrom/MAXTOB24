# Очередь исходящих и безопасная остановка

Исходящие Open Lines → MAX (отправка, правка, удаление) обрабатываются синхронно: `/webhook/b24`
отвечает Б24 **после** доставки в MAX. С M29 поверх этого работают три механизма:

- **Очередь по чату.** Исходящие одного чата идут строго по очереди: правка и удаление,
  пришедшие, пока мост заливает файл в MAX, ждут её и находят сообщение в MAX. Порядок
  держится только для событий, уже пришедших в мост: Б24 присылает событие о файле, лишь когда оператор полностью загрузил его в Битрикс24, поэтому текст, отправленный во время такой загрузки, приходит в MAX раньше файла — это порядок Б24 (live 2026-10-09).
- **Строка «в процессе»** в `message_log` на время каждого задания. Она отсекает параллельный
  повтор того же события, а если процесс умер посреди передачи, по ней следующий старт
  оповещает оператора.
- **Остановка с дренажом.** По `SIGTERM` порт остаётся открытым, пока очередь не опустеет и
  не ответят HTTP-запросы в работе: деплой посреди передачи файла дожидается её конца.

Зачем: Б24 событие не повторяет («Повторных отправок нет» — дока событий Б24). Закрытый порт
или убитый посреди передачи процесс означал бы потерянное сообщение оператора, о котором
никто не узнает. Б24 шлёт события одного чата параллельно, не дожидаясь ответа на предыдущее
(live M22), поэтому без очереди удаление во время заливки получало `no-maxmid`, и файл
оставался в MAX.

## Поток

```
POST /webhook/b24  (auth[application_token], member_id — без изменений)
  → b24Controller.handleWebhook
  → b24Service.handleOpenLineMessageAdd / Edit / Delete
  → messagingService.routeOutboundQueued(kind)           # kind: 'add' | 'edit' | 'delete'
      по каждому сообщению события, в его порядке:
        ├─ резолв привязки → invalid-message / no-binding / binding-not-ready сразу в ответ
        ├─ claim: INSERT job:<ключ операции>, status='in_progress'   конфликт → duplicate-in-progress
        └─ задание → очередь своего чата (KeyedQueue, ключ — connectorChatId)
              _runOutboundJob: прежний маршрут одного сообщения
                (routeOutbound / Edit / Delete: _once, файлы, оповещение оператора, статус доставки)
              → INFO outbound job done; DELETE строки job: (всегда, в finally)
      ответ Б24 — когда выполнены все задания события; форма прежняя
```

- **Задание — прежний маршрут.** Дедуп `_once`, файлы по одному под семафором, оповещение
  оператора о недоставке и статус доставки работают как раньше
  ([Outbound Routing](outbound-routing.md), [Media Transfer](media-transfer.md)). Привязку и
  токены портала задание читает заново, а не из вебхука: оно могло ждать очереди, а токен — за
  это время обновиться.
- **Ошибки.** Внутренняя ошибка отправки (БД, баг) → ERROR `outbound job failed`, оповещение
  «могло не дойти» и 500, как раньше. Ошибка одного сообщения не отменяет остальные сообщения
  события: они уже в очереди и выполнятся, а ответ всё равно 500. Если упал сам claim
  отправки (БД), в MAX ничего не ушло: остальные сообщения события не ставятся, оператор
  получает оповещение «могло не дойти», ответ — 500. Ошибки правки и удаления, в том числе
  ошибка claim, дают вердикты `edit-error` / `delete-error` с оповещением, без 500.
- **Новый вердикт** `duplicate-in-progress` — то же событие уже в работе. Ответ 200:
  `{"ok":true,"result":{"ok":true,"results":[{"skipped":"duplicate-in-progress"}]}}`. Раньше
  два одновременных одинаковых события оба проходили `_once` и давали дубль в MAX. Повтор
  после завершения по-прежнему получает `duplicate` (`duplicate-edit`, `duplicate-delete`).

## Порядок внутри чата

| Гарантировано | Не гарантировано |
|---|---|
| Отправка, правка и удаление одного чата выполняются по одному, в порядке постановки в очередь | Порядок сообщений в ОЛ. Место в очереди задаёт порядок, в котором события дошли до моста (точнее, завершили claim). События, пришедшие почти одновременно, могут переставиться: «три файла одним сообщением» с десктопа — это три события |
| Текст, событие которого пришло в мост, пока тот заливает файл в MAX, уходит после файла | Порядок сверх лимита очереди чата (ниже). Порядок файла и текста, пока оператор ещё загружает файл в Битрикс24: событие о файле Б24 присылает только после загрузки, текст придёт раньше (live 2026-10-09) |
| Правка и удаление во время заливки файла ждут её и работают с mid файла: ни `no-maxmid`, ни ложного «сообщение не найдено» | |
| Разные чаты не ждут друг друга | |

- **Передачи файлов.** Разные чаты идут параллельно, все передачи процесса — под общим
  семафором `MEDIA_CONCURRENCY` (по умолчанию 2). Файлы одного чата идут по одному, поэтому
  пачка больших файлов в одну группу доставляется за сумму времён передач, а не за время
  самой долгой.
- **Ответ Б24 на событие, вставшее за файлом, приходит после файла.** Текст, событие которого пришло,
  пока мост заливает файл 60 МБ в MAX, получит ответ через ~16–31 с вместо обычных ~0,5 с. По доке Б24
  медленный обработчик понижает приоритет очереди событий приложения. Смотреть `responseTime`
  в access-логе `POST /webhook/b24` и `queuedMs` в `outbound job done`. Если ответы
  систематически долгие и события Б24 начинают приходить с задержкой, нужна асинхронная
  обработка с ответом до доставки.
- **Обрыв соединения со стороны Б24 или Caddy** обработчик не прерывает: задание доходит до
  конца, запись в журнал пишется.

### Лимит очереди чата — `OUTBOUND_QUEUE_MAX`

По умолчанию 20 принятых и незавершённых заданий на чат. Если очередь чата полна, новое
задание выполняется **сразу**, без ожидания и вне порядка, с WARN
`outbound chat queue full, processing without waiting` (`connectorChatId`, `pending`, `max`).
Событие не отклоняется и не теряется, дренаж при остановке ждёт и такое задание.

Лимит — страховка от зависшей передачи (худший теоретический случай — ~1200 с: скачивание и
заливка по 300 с, ~150 с ожидания готовности в MAX, и столько же ещё раз на перезаливку файлом,
если MAX отверг тип вложения — [media-transfer.md](media-transfer.md)), а не рабочий режим. Обычная пачка —
2–3 события. Задание, обошедшее очередь, может снова обогнать заливку файла, тогда возможны
`no-maxmid` и оповещение «не найдено» (поведение до M29). Значение меняется через env без
кода ([env.md](env.md#очередь-исходящих-и-остановка-опциональные--есть-дефолты)).

## Строки заданий в `message_log`

Координатор пишет строку журнала перед постановкой задания в очередь, задание снимает её в конце
(`DELETE`, даже при ошибке):

| Поле | Значение |
|---|---|
| `direction` | `outbound` |
| `b24_msg_id` | `job:<ключ операции>`: `job:<im.message_id>` (отправка), `job:edit:<im.message_id>:<хеш текста>` (правка), `job:delete:<im.message_id>` (удаление). Ключ операции — тот же, под которым маршрут пишет свой результат |
| `status` | `in_progress` (у всех остальных строк журнала — `received`) |
| `payload_meta` | `{ kind:'job', op, opKey, connectorChatId, b24ChatId, b24MsgId }`; у отправки ещё `textPrefix`, `hasText`, `filesCount`, `fileNames` — для оповещения после рестарта; у удаления — `externalIds` (id сообщений MAX из события) для повтора после рестарта |

- **Миграции нет.** У `status` нет CHECK, а уникальный индекс `(binding_id, direction,
  b24_msg_id)` (`message_log_outbound_dedup_idx`) бесплатно даёт guard: второй claim того же
  ключа возвращает пусто → `duplicate-in-progress`. Строка `job:42` не мешает записи `42`.
- **В покое строк нет.** Строка живёт столько, сколько задание (обычно секунды). Оставшаяся
  строка означает либо задание, идущее сейчас, либо передачу, прерванную прошлым процессом.
- **Персональные данные.** В строке отправки лежат имена файлов (в имени бывает ФИО:
  «Паспорт Иванова.pdf») и до 32 символов текста. Строка удаляется по завершении задания или
  при разборе на следующем старте.
- **Удаление приложения Б24 с `CLEAN=1`** ([App Installation](app-installation.md#удаление-и-переустановка-m26))
  уносит строки каскадом вместе с привязками: снятие вернёт 0 (DEBUG `outbound job row already gone`).
- `make audit-bindings` считает строки `job:` среди исходящих — для аудита это несущественно.

Проверка (на проде — read-only):

```bash
docker compose exec -T database-postgres psql -U appuser -d appdb -c \
  "SELECT id, binding_id, b24_msg_id, created_at, payload_meta->>'op' AS op
     FROM message_log WHERE status = 'in_progress' ORDER BY id;"
```

Пусто в покое — норма. Строки есть — сейчас идёт передача (перед ручным рестартом её можно
дождаться) или прошлый процесс не успел их разобрать (см. [Troubleshooting](#troubleshooting)).

## Остановка: дренаж с открытым портом

`server.js` вешает обработчики `SIGTERM` и `SIGINT` и передаёт их в
`shared/lifecycle/gracefulShutdown.js`:

1. Разбор прерванных передач (если ещё идёт) прекращается: недоразобранные строки дождутся
   следующего старта.
2. INFO `shutdown requested: draining outbound queue (still listening)` (`pending` — заданий в
   очереди, `requests` — HTTP-запросов в работе). **Порт открыт:** новые события Б24 и MAX
   обрабатываются как обычно, `/health` отвечает 200.
3. Дренаж до `SHUTDOWN_DRAIN_TIMEOUT_MS` (по умолчанию 170 с): ждёт момента, когда **одновременно**
   очередь пуста и HTTP-запросов в работе нет. Запросы считаются наравне с очередью: событие Б24,
   которое ещё проверяет токен и делает claim, в очереди не видно, а закрой порт по пустой
   очереди — его передача шла бы уже при закрытом порте, и события других чатов получали бы
   502. То же со входящим MAX → ОЛ в работе. Уложились → INFO `outbound queue drained`, иначе
   ERROR `drain timeout: interrupted jobs will be reported on next start` (`pending`, `requests`).
4. `server.close()` закрывает порт и ждёт открытые HTTP-запросы (после шага 3 их обычно нет).
5. Повторный дренаж на остаток дедлайна (задания из запросов, пришедших, пока закрывался
   порт; обычно очередь уже пуста), затем `pool.end()`.
6. INFO `shutdown complete` (`code`, `durationMs`) и выход: **0**, если очередь опустела,
   **1**, если вышел дедлайн.

- **Keep-alive.** С первого сигнала ответы уходят с `Connection: close`: прокси не шлёт в
  такое соединение новых запросов, и оно закрывается сразу после ответа. После `server.close()`
  простаивающие соединения закрываются раз в секунду. Иначе Node продолжал бы принимать запросы
  по открытым keep-alive соединениям и после закрытия порта, а закрытие ждало бы `keepAliveTimeout`.
- **Жёсткий таймер** — дедлайн + 5 с (175 с): если закрытие повисло, ERROR
  `graceful shutdown timeout — force exit` и выход 1.
- **Повторный `SIGTERM`** дренаж не обрывает (WARN `shutdown: repeated signal ignored, still draining`):
  Docker шлёт его заново на каждый `docker stop`, `restart` и пересоздание контейнера —
  например, при ручном `docker stop`/`restart`, пока старый процесс ещё дренирует (повтор
  деплоя `FROM=up` сначала ждёт выхода прежнего `compose up`, см.
  [vps-prod.md](../deploy/vps-prod.md) §4). Время и так ограничено дедлайном и жёстким таймером.
- **`SIGINT` во время остановки** (второй Ctrl+C в терминале) — сразу выход 1 (WARN
  `shutdown: second signal, force exit`). Прерванное оповестит следующий старт.
- **Прерванное не теряется молча.** Задания, не дошедшие до конца к выходу, оставляют строки
  `job:`, и следующий старт оповестит оператора (ниже).

При пустой очереди остановка занимает доли секунды.

### Docker и деплой

| Величина | Значение | Где |
|---|---|---|
| Дедлайн дренажа | 170 с | `SHUTDOWN_DRAIN_TIMEOUT_MS` |
| Жёсткий таймер процесса | дедлайн + 5 с = 175 с | `gracefulShutdown.js` (`closeTimeoutMs`) |
| Grace контейнера (`StopTimeout`) | 180 с | `stop_grace_period: 180s` у `api-node` в `docker-compose.server.yml` |
| Reboot VPS | ~90 с | `TimeoutStopUSec` у `docker.service` (systemd) |

- **170 с** покрывают один проход файла 256 МиБ на замеренной полосе VPS (из Б24 ~53 МБ/с, в
  MAX ~43 МБ/с — скачивание и заливка по ~5–6 с) с полным ожиданием готовности в MAX (~150 с).
  Перезаливка отвергнутого MAX типа файлом (M28) — второй проход в том же задании: ещё заливка и,
  если MAX отказал на `POST /messages`, ещё ожидание готовности. Такая большая передача, как и
  передача на просевшей полосе, в дедлайн может не уложиться — её оповестит следующий старт
  («мост перезапускался»). Поднять дедлайн можно только вместе с `stop_grace_period`.
  `stop_grace_period` держите больше дедлайна не меньше чем на 10 с: жёсткий таймер процесса
  (дедлайн + 5 с) должен срабатывать раньше `SIGKILL` Docker. При зазоре 5 с они совпадают, и
  обычно побеждает `SIGKILL`: выход 137 без закрытия пула и без `shutdown complete`. Длинный grace простоя не добавляет (порт открыт), он только
  удлиняет деплой.
- **PID 1 — `node server.js`** (`CMD` прод-стадии `Dockerfile`). Ядро не применяет к PID 1
  действие сигнала по умолчанию: без обработчиков `SIGTERM` игнорировался бы, и `docker stop`
  кончался бы `SIGKILL` по истечении grace.
- **Деплой ждёт дренажа.** `make deploy` (шаг `up`), `make prod-up`, `make prod-up-db`, `make prod-down`,
  `docker stop`/`restart` и `compose up -d` с пересозданием `api` ждут выхода старого процесса
  — до 3 мин. Новый контейнер стартует после выхода старого. Разрыв между ними ~0,6–1 с
  (замер 2026-10-08), это и есть простой деплоя: ~1 с на старт процесса. У `make prod-up-db`
  (изменения сервиса БД) разрыв дольше: между ними пересоздание БД и миграции — БД меняется
  только после дренажа `api`.
- **Grace пишется в контейнер при создании.** Первое пересоздание после появления
  `stop_grace_period` останавливает старый контейнер по его прежним 10 с. Поэтому **первый
  деплой этой версии** идёт по старым правилам: старый код порт сразу закрывает и строк `job:`
  не пишет, так что передача, идущая в этот момент, теряется без оповещения. Выкатывать, когда
  операторы не шлют файлы (в `docker logs --since 5m api` нет свежих `routeOutboundFile`).
  Дренаж работает с любой остановки после выката. Проверка:
  `docker inspect api --format '{{.Config.StopTimeout}}'` → `180`.
- **Перезапускайте `api-node`, а не весь стек.** `compose restart` без имени сервиса шлёт
  `SIGTERM` и Postgres: БД уходит посреди дренажа, и задания, которым в это окно нужна БД,
  падают. Порядок — в [vps-prod.md §10](../deploy/vps-prod.md#10-выживание-после-рестарта--reboot).
- **Вне Docker** запускайте `node server.js`, не `pnpm start`: на хосте pnpm по `SIGTERM`
  умирает сразу (код 143), не передав сигнал node, и процесс моста остаётся сиротой (проба
  2026-10-08). В контейнере pnpm как PID 1 сигнал передаёт, но с M26 его там нет.
- **На dev-стеке** (`make dev-node`) дренаж не проверить: у dev-контейнера grace по умолчанию —
  10 с, а node запущен через `sh -c`, pnpm и nodemon. Проверять дренаж — на прод-стадии образа
  или `node server.js` на хосте.

## Старт: передачи, прерванные прошлым процессом

Процесс открывает порт сразу, не дожидаясь БД: у пула нет `connectionTimeoutMillis`, и запрос
к недоступной БД до `listen` повесил бы старт. После `server listening`, не блокируя приём
событий, `recoverInterruptedOutbound` ищет строки `in_progress`, созданные **раньше момента
старта процесса** (свои новые задания не попадают):

- ошибка БД при поиске → WARN `interrupted outbound lookup failed, retrying`, до 5 попыток с
  паузой 5 с (после reboot Postgres может подняться позже api). Исчерпано → ERROR
  `interrupted outbound lookup gave up (rows wait for next start)`;
- за старт — до 500 строк, остальное разберёт следующий старт;
- строки разбираются **через очередь своего чата**: сразу после поиска очередь каждого
  затронутого чата занимается одним заданием, внутри которого строки этого чата идут по одной,
  в порядке `id`. События, пришедшие после поиска, встают за разбором своего чата: удаление
  частично ушедшего сообщения находит дописанные части. Лимит очереди чата не забивается
  (одно место на чат), чаты разбираются параллельно, дренаж при остановке ждёт и разбор.
  Событие, успевшее прийти между `server listening` и концом поиска (обычно миллисекунды,
  дольше — если БД ещё не поднялась), разбор может обогнать;
- остановка во время разбора его прерывает (INFO `interrupted outbound recovery stopped by shutdown`, `left`).

| Строка | Что делает разбор | Оповещение |
|---|---|---|
| Операция уже записана в журнал (процесс упал между записью и снятием строки) | только снимает строку | нет |
| Отправка | ушедшие файлы (`file:<im.message_id>:<n>`) дописывает итоговой записью (`interrupted: true`, `sentAt` — время первой ушедшей части, по нему возраст в «MAX не разрешил удалить») и шлёт статус доставки: удаление в ОЛ потом сотрёт их в MAX | о недоставленных файлах и тексте |
| Удаление | повторяет удаление обычным путём по mid из журнала и из события (`externalIds` строки): повторный `DELETE` уже удалённого mid MAX отвечает `success:true` | только если MAX отказал или внутренняя ошибка (тексты [Message Deletion](message-deletion.md#исходы-и-оповещения-оператора)); `no-maxmid` — без оповещения |
| Правка | повторить нечем: текста правки в журнале нет | «правка не доставлена» |
| Отправка или правка сообщения, удаление которого тоже прервано | отправку только дописывает в журнал (удаление сотрёт части), правку пропускает | нет — оператор сообщение удалил |
| Привязки нет / строка без нужных полей | снимает строку (WARN `… dropped`) | нет |

Строка снимается **всегда**, после разбора: повторного оповещения на следующем старте нет.

**Оповещения** — системные сообщения в чат ОЛ через `notifyOperator`
([Outbound Routing](outbound-routing.md#оповещение-оператора-m28)), с причиной
`мост перезапускался`:

```
⚠️ Не доставлено в MAX: файл «Договор.pdf» — мост перезапускался; файл «Скан.jpg» — мост перезапускался. Отправьте ещё раз.
⚠️ Не доставлено в MAX: текст сообщения — мост перезапускался. Отправьте ещё раз.
⚠️ Правка не доставлена в MAX: мост перезапускался. У клиентов осталась прежняя версия — отредактируйте сообщение ещё раз.
```

- **Не ответом на сообщение.** У системного сообщения Б24 `REPLY_ID` не сохраняет (проба
  2026-10-08), а цитаты текста в журнале нет. Сообщение с файлами оператор узнаёт по именам
  файлов; файл без имени назван «файл N». Какое именно текстовое сообщение не ушло, из
  оповещения не видно: при дренаже такое бывает только после жёсткого убийства процесса,
  дедлайна дренажа или reboot.
- **Текст** попадает в список, если у сообщения есть текст или подпись и она не ушла ни с
  одним файлом.
- **Повторы.** Б24 не принял оповещение → ещё 2 попытки с паузами 2 и 5 с, затем ERROR
  `recovery notice failed, giving up`, и строка снимается. Нет чата ОЛ (`no-chat`) — без повторов.

## Логи

**Очередь** (с `requestId` вебхука):

| Лог | Когда |
|---|---|
| INFO `outbound job done` | задание выполнено: `op`, `bindingId`, `connectorChatId`, `b24MsgId`, `verdict` (`ok` или skip-вердикт), `queuedMs` — сколько ждало очереди чата, `durationMs`, `bypass` |
| ERROR `outbound job failed` | внутренняя ошибка отправки (БД, баг) → 500; те же поля + `err` |
| WARN `outbound chat queue full, processing without waiting` | очередь чата полна, задание идёт вне порядка (`pending`, `max`) |
| WARN `routeOutbound: duplicate-in-progress, skipping` (`routeOutboundEdit:` / `routeOutboundDelete:`) | то же событие уже в работе (`opKey`) |
| ERROR `routeOutbound: outbound job claim failed, not queued` | БД отказала на claim отправки → оповещение «могло не дойти», 500 |
| WARN `outbound job release failed, retrying in background` | строка не снялась (БД); повторы в фоне через 5 с, 30 с, 2 мин и 10 мин — ответ и очередь чата их не ждут |
| INFO `outbound job released after retry` | строку снял повтор (`attempt`) |
| ERROR `outbound job release gave up (will be reported on next start)` | БД недоступна ~12,5 мин: строка дождётся следующего старта (см. [Troubleshooting](#troubleshooting)) |
| DEBUG `messageLog.claimOutboundJob` / `releaseOutboundJob`, `outbound job row already gone` | claim и снятие строки |

**Остановка:**

| Лог | Когда |
|---|---|
| INFO `shutdown requested: draining outbound queue (still listening)` | сигнал получен (`signal`, `pending`, `requests` — HTTP-запросов в работе, `drainTimeoutMs`) |
| INFO `outbound queue drained` | очередь пуста и запросов в работе нет (`durationMs`) |
| ERROR `drain timeout: interrupted jobs will be reported on next start` | дедлайн дренажа (`pending`, `requests`) |
| INFO `http server closed` / `pg pool closed` | порт и пул закрыты (ошибки — ERROR `http server close error` / `pg pool close error`) |
| INFO `shutdown complete` | выход (`code` 0 или 1, `durationMs`) |
| ERROR `graceful shutdown timeout — force exit` | жёсткий таймер: закрытие повисло (`timeoutMs`, `pending`) |
| WARN `shutdown: repeated signal ignored, still draining` | повторный `SIGTERM` (ещё один `docker stop`, повтор деплоя): дренаж продолжается |
| WARN `shutdown: second signal, force exit` | `SIGINT` во время остановки (второй Ctrl+C): выход 1 |
| ERROR `shutdown: onSignal failed`, `shutdown failed — force exit` | непредвиденная ошибка в самой остановке |

**Старт:**

| Лог | Когда |
|---|---|
| DEBUG `no interrupted outbound jobs` | прерванных нет (норма) |
| INFO `interrupted outbound jobs found` | найдены строки прошлого процесса (`count`) |
| WARN `interrupted outbound lookup failed, retrying` / ERROR `… lookup gave up (rows wait for next start)` | БД недоступна на старте |
| INFO `interrupted outbound job: already done` | операция была записана, строка снята |
| INFO `interrupted outbound send: delivered parts recorded` | ушедшие файлы дописаны в журнал (`delivered`, `filesCount`) |
| INFO `interrupted outbound delete retried` | удаление повторено (`verdict`) |
| INFO `interrupted outbound send: message deleted later, not notifying` / `interrupted outbound edit: …` | сообщение удалено оператором, оповещения нет |
| WARN `interrupted outbound job: no binding, dropped` / `… malformed row, dropped` | строка снята без разбора |
| ERROR `recovery notice failed, giving up` | оповещение не ушло после 3 попыток (`reason`) |
| WARN `interrupted outbound job recovery failed, row released` | ошибка разбора одной строки, строка снята |
| INFO `interrupted outbound recovered` | итог: `total`, `notified`, `completed`, `dropped`, `failedNotify`, `failed` |
| INFO `interrupted outbound recovery stopped by shutdown` | разбор прерван остановкой (`left`) |

Оповещение о прерванном пишет обычные логи `notifyOperator` (`op`, `b24MsgId`); текст
оповещения в лог не попадает (там имена файлов).

## Troubleshooting

| Симптом | Причина | Действие |
|---|---|---|
| `make deploy` (шаг `up`), `prod-down` или `restart` висит до 3 мин | старый процесс дренирует очередь: идёт передача файла | Норма. В `docker logs api` — `shutdown requested…`, затем `outbound queue drained`. SSH деплоя такую паузу переживает (5 мин тишины) |
| После деплоя в ОЛ «⚠️ Не доставлено в MAX: … — мост перезапускался» | передача не уложилась в дедлайн дренажа, процесс убит (`docker kill`, OOM) или VPS перезагружался | Оператор отправляет ещё раз. Причина — в логе остановки: `drain timeout` или нет `shutdown complete`. После `restart` он в `docker logs api`; после пересоздания контейнера (деплой) — в journald: `make prod-journal` на VPS (M30, [vps-prod.md §5](../deploy/vps-prod.md#про-docker-composeserveryml-prod-override)) |
| «Не доставлено», а сообщение в MAX есть (дубль после повторной отправки) | процесс убит жёстко посреди запроса к MAX: MAX сообщение принял, записи в журнале ещё не было | Окно — один HTTP-запрос к MAX, риск принят. Штатная остановка с дренажом такого не даёт: только `SIGKILL`, OOM, дедлайн дренажа и reboot |
| После reboot VPS — оповещения «мост перезапускался» | systemd гасит `docker.service` не дольше 90 с, контейнеры — без порядка compose: Postgres может уйти раньше api | Ожидаемо. Если БД поднимается позже api, разбор повторяет поиск — до 5 попыток с паузой 5 с; не поднялась — строки ждут следующего старта (`… lookup gave up`) |
| Оповещения «мост перезапускался» без рестарта или после штатного рестарта с пустой очередью | второй процесс моста на той же БД (второй `api-node`, `node server.js` на хосте с прод-`DATABASE_URL`) | Мост single-tenant: на одну БД — один процесс. Чужие строки `in_progress` старше своего старта процесс принимает за прерванные, и оператор получает ложные оповещения |
| 502 у события Б24 при переключении контейнеров | окно ~1 с между выходом старого процесса и стартом нового; ретраев апстрима в Caddy нет ([vps-prod.md §6](../deploy/vps-prod.md#6-caddy-site-блок--tls)) | Б24 событие не повторит. Риск принят (M30): ~0,1 события в год. Одного `lb_try_duration` мало — нужны ещё `lb_retry_match` с POST и `request_buffers`; правка общего прокси — только по согласованию с соседом |
| Ответ на событие Б24 долгий (`responseTime` в секундах, `queuedMs` большой) | событие встало в очередь чата за передачей файла | Норма для файлов. Систематически долгие ответы и задержка событий Б24 — повод для асинхронной обработки |
| WARN `outbound chat queue full` | передача в чате зависла, а оператор продолжает писать | Зависшее задание видно в журнале: строка `in_progress` с давним `created_at` (SQL [выше](#строки-заданий-в-message_log)). Оно завершится само: скачивание и заливка ограничены `MEDIA_TRANSFER_TIMEOUT_MS`, ожидание готовности — `MAX_UPLOAD_MAX_RETRIES` |
| `duplicate-in-progress` в ответах | Б24 прислал событие повторно, пока первое ещё выполнялось | Норма: в MAX уходит одна копия |
| Строки `in_progress` в покое, без передач | процесс упал и ещё не стартовал, либо снятие строки не удалось и после повторов (ERROR `outbound job release gave up`) | Разберёт следующий старт. Вручную строки не удалять: тогда не будет оповещения о прерванном |
| Запоздалое «мост перезапускался» о давнем сообщении, хотя оператор уже получил оповещение о нём | строка не снялась и после повторов (ERROR `outbound job release gave up`), процесс работал дальше, а следующий старт принял её за прерванную. Если задание успело записать операцию, разбор строку просто снимает; если закончилось без записи (недоставка, `no-maxmid`, отказ MAX, `edit-error`/`delete-error`) — оповещение повторится, с другой причиной и без времени | Редко: нужна недоступность БД дольше ~12,5 мин сразу после задания. Сверить с ERROR `outbound job release gave up` (`jobId`) в логе прошлого процесса; повторно отправлять не нужно, если первое оповещение было о другой причине |
| «Могло не дойти», а ушедшие части файлов удаление в ОЛ не стирает | ошибка БД посреди отправки из нескольких файлов: части `file:<id>:<n>` записаны, итоговой записи нет | Известное ограничение (до M29 так же): удалить файлы в MAX вручную |
| Ошибка `drain timeout` при остановке и выход 1 | передача дольше `SHUTDOWN_DRAIN_TIMEOUT_MS` (зависший MAX, файл у лимита) | Оператор получит оповещение на старте. Поднимать дедлайн — только вместе с `stop_grace_period` |

## Конфигурация

| Env | Default | Назначение |
|---|---|---|
| `OUTBOUND_QUEUE_MAX` | `20` | лимит очереди одного чата, больше `1000` зажимается |
| `SHUTDOWN_DRAIN_TIMEOUT_MS` | `170000` | дедлайн дренажа; меньше `stop_grace_period` не меньше чем на 10 с |

Обе опциональны, невалидное значение — ошибка старта. Подробнее — [env.md](env.md#очередь-исходящих-и-остановка-опциональные--есть-дефолты).
