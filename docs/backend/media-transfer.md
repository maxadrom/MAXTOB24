# Передача файлов (медиа-мост MAX ↔ Open Lines)

Двусторонняя пересылка медиа (фото, видео, документы, стикеры) поверх текстового моста M1–M10, плюс входящие голосовые (`audio`, M11.3). Медиа — атрибут того же сообщения: идемпотентность по существующим ключам (`max_mid` / `b24_msg_id`, у исходящих файлов — ещё `file:<b24_msg_id>:<n>`, M22), **новой миграции нет** (метаданные в `message_log.payload_meta`). Исходящие файлы идут потоком через диск, недоставка видна оператору (M22); картинку, которую MAX не принимает как изображение, мост отправляет файлом (M28).

## Inbound (MAX → Open Lines)

```
POST /webhook/max (message_created с body.attachments[] и/или пересылкой link.message.attachments[])
  → maxService → messagingService.routeInbound
      ├─ MaxUpdate.attachments() → [{ kind, url, name }]   (image/file/video/sticker/audio)
      ├─ ConnectorMessage({ text, files:[{url,name}], ... })
      └─ b24Service.sendConnectorMessage → imconnector.send.messages
          message.files:[{url,name}]   ← Б24 качает файл сам по url
```

**Пересылка (M21).** У пересланного сообщения своё тело пустое (`body.text=''`, свой `mid` есть), а пересланное лежит в `message.link.message`: текст уходит цитатой `>>↪ Переслано` ([Reply Quoting](reply-quoting.md)), вложения — из `link.message.attachments` вместе со своими (свои первыми, повтор url не дублируется). Только для `link.type='forward'`: у `reply` там родитель, его медиа к ответу не относится. До M21 пересланная картинка с подписью доходила без картинки (live 2026-10-08).

| MAX type | url | name | Б24 |
|----------|-----|------|-----|
| `image` | `payload.url` (`i.oneme.ru`) | `<photo_id>.webp` | `files[{url,name}]` |
| `file` | `payload.url` (`fd.oneme.ru`) | `attachment.filename` | `files[{url,name}]` |
| `video` | `payload.url` (`vd*.okcdn.ru`) | `<id>.mp4` | `files[{url,name}]` |
| `sticker` | `payload.url` (`st.mycdn.me`) | `<code>.png` | `files[{url,name}]` (как картинка) |
| `audio` (голосовое, M11.3) | `payload.url` (`a.oneme.ru/audio`) | `<payload.id>.ogg` | `files[{url,name}]` (inline аудио-плеер по mime `audio/ogg`) |

- Неизвестный `type` или отсутствие `url` → файл пропускается с WARN (мост не падает).
- `empty-message` теперь только когда **нет ни текста, ни файлов**.
- `filename`/`size` (file) и `duration`/`thumbnail` (video) лежат на уровне attachment, НЕ в `payload`.

## Outbound (Open Lines → MAX)

Файлы оператора приходят в `OnImConnectorMessageAdd` `message.files[]` (вопреки доке Б24).

```
POST /webhook/b24 (ONIMCONNECTORMESSAGEADD с message.files[])
  → routeOutboundQueued('add')                    M29: строка job:<im.message_id> → очередь чата
  → задание очереди (маршрут routeOutbound)       _once по im.message_id (итог сообщения)
      ├─ OpenLineEvent.normalizedMessages() → files:[{name,mime,type,downloadLink,size,width,height}]
      └─ для каждого файла ПО ОЧЕРЕДИ, под семафором (MEDIA_CONCURRENCY) и своим
         _once по file:<im.message_id>:<n>:
            ├─ временный файл (MEDIA_TMP_DIR/<uuid>.part)
            ├─ b24Service.downloadOperatorFile   анонимно по downloadLink, ПОТОКОМ на диск
            ├─ тип: mime (allowlist картинок), стороны картинки, фактический размер
            └─ maxService.uploadAndSend
                  ├─ createUpload(type)          POST /uploads?type=…  → { url, token? }
                  ├─ uploadBinary(url, файл)     multipart ПОТОКОМ с диска, БЕЗ Authorization
                  ├─ sendMessage({attachments})  POST /messages + ретрай только «не готово»
                  └─ MAX отверг тип (не file) →  тот же временный файл ещё раз как file (M28)
            └─ запись file:<id>:<n>, временный файл удаляется (finally)
      → итоговая запись по im.message_id (maxMids всех файлов) → статус доставки (все maxMids)
      → недоставка → системное сообщение оператору в ОЛ (notifyOperator), ответ 200
```

- **Поток через диск (M22).** Файл не держится в памяти: скачивание — `pipeline` в `MEDIA_TMP_DIR` со счётчиком байт, заливка — `node:https.request` с multipart, собранным вручную, и явной `Content-Length` (встроенный `fetch` буферизует тело целиком). Замер 250 МБ (Node 22): пик RSS +45 МБ против +1,46 ГБ у прежнего пути через `Buffer`/`Blob`. На Node 24 (M26) тот же путь даёт пик +78–87 МБ против +41–46 МБ у Node 22 (медианы на хосте и в образе `node:*-alpine`): буферы чанков рантайм собирает позже — так же и на голом `node:http`, без `fetch`/undici. Пик ограничен: с размером файла он не растёт (250 и 500 МБ дают одинаковый). Замер — `scripts/probe-media-memory.js` (loopback, без сети и `.env`): `node scripts/probe-media-memory.js --size-mb=250` из `backends/node/api/`. Временный файл удаляется сразу после передачи, остатки после рестарта чистит `server.js` на старте. Диск под передачи — не больше `MEDIA_MAX_BYTES × MEDIA_CONCURRENCY`.
- **Дедлайны.** Скачивание и заливка — каждая не дольше `MEDIA_TRANSFER_TIMEOUT_MS` (по умолчанию 300 с). Дедлайн покрывает и тело ответа, а не только заголовки. Если MAX отверг тип и файл перезаливается (ниже), заливок две, и худшее время файла удваивается.
- **MAX-тип** (`maxUploadTypeForFile` в `max/maxService.js`): `video/*` → `video`, `audio/*` → `audio`, картинка → `image` (правила ниже), иначе `file`. Больше лимита MAX своего типа (картинка 50 МБ, видео 250 МБ, аудио 256 МБ — dev.max.ru, в десятичных МБ) → `file`: превью не будет, зато файл дойдёт.
  - **Картинка — `image`, только если MAX её примет (M28):** mime из списка JPG/JPEG/PNG/GIF/TIFF/BMP/WEBP (`image/jpeg`, `image/jpg`, `image/pjpeg`, `image/png`, `image/gif`, `image/tiff`, `image/bmp`, `image/x-ms-bmp`, `image/webp`; параметры вроде `; charset=…` отрезаются) и каждая сторона не больше **7680 px** по `width`/`height` из события Б24. Файл с `type:'image'` от Б24, но без `image/*` в mime — тоже `image`, как раньше.
  - **Остальные `image/*` (HEIC/HEIF, SVG, ICO, AVIF, PSD…) и картинка со стороной больше 7680 px — сразу `file`:** MAX их картинкой не примет, а заливка до 50 МБ ушла бы впустую. Список — по доке MAX с поправкой на пробы 2026-10-08: WEBP в доке нет, но MAX его принимает; HEIC в доке есть, но MAX отвечает `IMAGE_INVALID_FORMAT`, как и на SVG. Лимит 7680 px — по каждой стороне, а не по площади: 7700×300 → `IMAGE_DIMENSION_CHECK_FAIL`. Нет размеров в событии — проверку сторон пропускаем, отказ поймает перезаливка.
  - `width`/`height` картинки пишутся в INFO `routeOutboundFile: file delivered to MAX` — по ним видно, ушла ли картинка файлом превентивно.
- **Отвергнутый тип → `file` (M28).** Картинке MAX отказывает не ошибкой HTTP, а ответом **200** на шаге заливки — без `photos`, с кодом в `error_data`: `{"error_code":"503","error_data":"IMAGE_INVALID_FORMAT"}` или `{"error_code":"1","error_data":"IMAGE_DIMENSION_CHECK_FAIL"}` (пробы 2026-10-08; `error_code` — внутренний код MAX, не HTTP-статус, не читается). Код из `error_data` попадает в `MaxApiError.maxCode`. Allowlist ловит не всё: PNG 1×1 MAX тоже отвергает как `IMAGE_INVALID_FORMAT`. Поэтому, если MAX отверг не-`file` тип (`image`, `video`, `audio`) там, где сообщение в MAX точно не создано, тот же временный файл заливается ещё раз как `file` — без повторного скачивания, в том же слоте `MEDIA_CONCURRENCY` и под тем же ключом `file:<id>:<n>`, так что запись одна (`isMediaRejectedError` в `max/maxService.js`):

  | Шаг (`MaxApiError.stage`) | Перезаливка файлом | Без перезаливки |
  |---|---|---|
  | `POST /uploads` (`create`) | — | любая ошибка, нет `url` в ответе |
  | заливка (`upload`) | 4xx, кроме 429 | 429, 5xx, таймаут, сеть |
  | разбор ответа заливки (`payload`) | 2xx без `photos`/токена — живая форма отказа; у `video`/`audio` (токен выдаёт `/uploads` до заливки) — 2xx с `error_data` без своего токена | — |
  | `POST /messages` (`send`) | 400, кроме `attachment.not.ready` и слишком длинной подписи | `403 chat.denied`, исчерпанное «не готово», 400 `proto.payload` `Field 'text' size …` (файлом ушла бы та же подпись), 429, 5xx, таймаут, сеть |

  4xx на заливке и 400 на `POST /messages` у картинок пока не наблюдались — перезаливка там страховка: сообщение в MAX не создано, повтор безопасен. Перезаливка одна; её ошибка уходит оператору обычной недоставкой. Оператора о том, что картинка ушла файлом, не оповещаем — только WARN `uploadAndSend: MAX rejected attachment type, re-uploading as file` (`type`, `stage`, `httpStatus`, `maxCode`) и `fallbackFrom` в журнале. Как MAX отказывает видео (вне MP4/MOV/MKV/WEBM), live не снято: ответ заливки с `error_data`, как у картинки, перезаливка ловит (код — в `maxCode` WARN), а бесконечное «не готово» на `POST /messages` — нет.
- **Готовность вложения.** Сразу после заливки MAX отвечает на `POST /messages` **HTTP 400** `attachment.not.ready` (`errors.process.attachment.file.not.processed`, у видео — `…video.not.processed`). Повторяется только этот шаг, файл не перезаливается: паузы 1, 2, 4, 8, дальше по 15 с, `MAX_UPLOAD_MAX_RETRIES` попыток (по умолчанию 14 ≈ 150 с). Live 2026-10-08: файл 60 МБ стал готов через 16–31 с, видео 30 МБ — через 3 с. Повтор также на 429. Таймаут, сеть, 5xx и прочие 4xx (например, `403 chat.denied` — бот не в чате) — без повтора: после таймаута сообщение могло уже уйти.
- **`downloadLink`** (`https://<portal>/pub/im.file.php?FILE_ID=…&SIGN=…`) скачивается анонимно (SIGN в url несёт авторизацию), каждый хоп редиректа проходит SSRF-guard.
- **Подпись оператора** (`resolveMediaCaption` в `b24/bbcode.js`): реальный комментарий идёт подписью к первому **доставленному** файлу; авто-ярлык Б24 `[b]Имя:[/b] [br]<имя файла>` (файл без комментария) подавляется. Не ушёл ни один файл, а комментарий есть → комментарий уходит текстом.
- **`MEDIA_MAX_BYTES`** (по умолчанию 256 МиБ): заявленный в событии размер больше лимита → файл не скачивается; `Content-Length` больше лимита → тело не читается; без `Content-Length` поток обрывает счётчик байт. Во всех случаях файл пропускается, оператор получает системное сообщение.

### Очередь чата и рестарт посреди передачи (M29)

Исходящие одного чата — отправка, правка, удаление — идут через очередь чата строго по одному
([Outbound Queue](outbound-queue.md)):

- **Файлы одного чата — по одному.** Файл из следующего события того же чата ждёт, пока
  уйдёт предыдущий: семафор `MEDIA_CONCURRENCY` делят только разные чаты. Пачка больших файлов
  в одну группу доставляется за сумму времён передач, а не за время самой долгой. Три файла,
  отправленные с десктопа «одним сообщением», — это три события Б24; их порядок в MAX задаёт
  порядок прихода событий в мост.
- **Текст, пришедший в мост во время заливки файла в MAX,** уходит после файла (если оператор
  ещё загружает файл в Битрикс24, Б24 пришлёт событие о файле только после загрузки — текст
  придёт раньше). **Правка подписи и удаление**, пришедшие во время заливки, ждут её и работают
  с mid файла. Ответ Б24 на такое событие приходит после
  заливки.
- **Рестарт посреди передачи.** По `SIGTERM` мост держит порт открытым и дожидается конца
  передачи — до `SHUTDOWN_DRAIN_TIMEOUT_MS` (170 с); `stop_grace_period` контейнера — 180 с.
  Если процесс всё же прерван (дедлайн, `docker kill`, OOM, reboot), строка задания `job:`
  остаётся в журнале, и следующий старт:
  - дописывает уже ушедшие файлы (`file:<im.message_id>:<n>`) итоговой записью и шлёт статус
    доставки — удаление в ОЛ потом сотрёт их в MAX;
  - об остальном оповещает оператора: `⚠️ Не доставлено в MAX: файл «Скан.jpg» — мост
    перезапускался. Отправьте ещё раз.` (не ответом на сообщение: у системного сообщения Б24
    `REPLY_ID` не сохраняет).

  Временные файлы прерванной передачи `server.js` удаляет на старте, как и раньше.

### Недоставка → системное сообщение оператору (M22)

Б24 событие не повторяет, поэтому ответ 5xx ничего не исправит, а оператор не узнает, что клиент файл не получил. Если файл (или текст) не ушёл в MAX, остальные файлы сообщения всё равно отправляются, вебхук отвечает 200, а в чат ОЛ уходит одно системное сообщение (`im.message.add`, `SYSTEM=Y` — клиенту в MAX не пересылается). Шлёт его общий для отправки, правки и удаления `notifyOperator` — контракт и логи в [Outbound Routing](outbound-routing.md#оповещение-оператора-m28):

```
⚠️ Не доставлено в MAX: файл «report.pdf» — больше 256 МиБ; файл «a.mp4» — MAX не принял (attachment.not.ready). Отправьте ещё раз.
```

| Причина в сообщении | Когда |
|---|---|
| `больше N МиБ` | файл больше `MEDIA_MAX_BYTES` |
| `не удалось скачать из Битрикс24` / `не скачался из Битрикс24 вовремя` | `downloadLink` вернул ошибку / истёк дедлайн скачивания |
| `MAX не принял (<code>)` / `MAX не принял (HTTP <status>)` | MAX ответил ошибкой (в т.ч. «не готово» после всех попыток) или отверг `file` кодом в `error_data` ответа заливки (M28). Отказ картинки, видео или аудио сначала перезаливается файлом — оператор видит причину, только если упала и перезаливка, и это причина перезаливки |
| `MAX не ответил вовремя` / `MAX недоступен` / `MAX вернул неожиданный ответ` | таймаут / сеть / в ответе нет `url` или токена, а кода отказа нет |
| `текст слишком длинный (N символов при лимите MAX M)` | подпись вместе с подписью оператора длиннее 4000 символов — MAX ответил 400 `proto.payload` `Field 'text' size (N) must be at most M` (лимит — схема MAX и live 2026-10-09). Отказ получает каждый файл, с которым уходила подпись, и сама подпись текстом — в оповещении они свёрнуты в один пункт (M30): `текст слишком длинный (N символов при лимите MAX 4000) — файлы «a.jpg», «b.jpg» и подпись`. Без чисел в ответе — `текст слишком длинный для MAX` |

В логе каждый файл, не дошедший до MAX, — ERROR `routeOutbound: file not delivered to MAX` с полями `idx`, `mime`, `b24Type` (тип файла из события Б24; `type` в строках доставки — уже тип заливки MAX), `reason`, `err` (M30). По `mime` видно, не отвергает ли MAX какой-то формат видео, — на проде лог в journald (`make prod-journal`).

Хвост сообщения — что делать оператору: файл больше лимита повтор не пропустит, поэтому для него «Загрузите на диск и отправьте как ссылку.»; слишком длинный текст — тоже, поэтому «Сократите текст или разбейте его на несколько сообщений.»; для остальных причин — «Отправьте ещё раз.»; при смеси подсказки складываются через запятую («Большие файлы загрузите на диск и отправьте как ссылку, текст сократите или разбейте на несколько сообщений, остальное отправьте ещё раз.»).

Вердикт в ответе вебхука: частичный успех — `{ ok: true, maxMids, failedFiles }`, ничего не ушло — `{ skipped: 'delivery-failed' }`, то же событие ещё заливается — `{ skipped: 'duplicate-in-progress' }` (M29). Ошибки БД и баги по-прежнему дают 500, а оператору уходит best-effort оповещение `⚠️ Сообщение могло не дойти до MAX: внутренняя ошибка моста…` (M28). Сбой самого оповещения только логируется. Имена файлов и причины в тексте экранируются от BB-кодов.

## Голосовые (M11.3)

Входящие голосовые из MAX (`message_created`, `attachment type:"audio"`, host `a.oneme.ru/audio`, `payload:{url,token,id}`, без `filename`) форвардятся в Open Lines поверх готового медиа-пути M11.2 — без новой миграции и без отдельной ветки в координаторе.

- **Минимальная правка:** `audio` добавлен в `ATTACHMENT_KINDS` (`MaxUpdate.attachments()`), имя файла — `<payload.id>.ogg`. Дальше работает существующий путь `files:[{url,name}]` → `imconnector.send.messages` (Б24 качает `.ogg` по url сам, скачивание анонимное).
- **Рендер:** Б24 определяет `type=audio` по mime `audio/ogg` (Opus) → сообщение показывается **встроенным аудио-плеером**, а не ссылкой «скачать файл».
- **Идемпотентность/миграции не менялись:** дедуп по `max_mid` цел, `payload_meta` получает `kinds:["audio"]` автоматически.
- **Outbound voice (OL → MAX) платформенно невозможен:** у оператора в Открытых линиях нет записи голосового (десктоп и мобайл — микрофон = диктовка в текст). Аудио-ФАЙЛ, вложенный скрепкой, уходит как обычный файл (mime `audio/*` → `type=audio` upload, механика M11.2 выше).
- **PTT-«пузырёк» (`isVoiceNote`) недостижим:** это read-only свойство Disk-файла, выставляется только нативным клиентом Б24; через `imconnector`/REST не выставить. Потолок — inline-плеер.

## Идемпотентность

- Входящие — по `max_mid`; `recordInbound` пишет `{ filesCount, kinds }` в `payload_meta`.
- Исходящие (M22) — две ступени, миграции нет (частичный индекс `b24_msg_id` покрывает и синтетические ключи):
  - **файл** — `file:<im.message_id>:<n>`, `payload_meta { kind:'file', origB24MsgId, idx, maxMid, type, mime, size, withCaption, fallbackFrom? }`: `type` — фактический тип в MAX, `fallbackFrom` — исходный, если MAX его отверг и файл ушёл как `file` (M28). Повтор события не шлёт уже ушедшие файлы: `maxMid` берётся из записи;
  - **сообщение** — «голый» `im.message_id`, пишется, если в MAX ушла хоть одна часть: `{ maxMid, maxMids, filesCount, kinds, failedCount? }` (`kinds` — фактические типы). Ничего не ушло → записи нет, повтор события попробует заново. Запись, дописанная на старте после прерванной передачи (M29), несёт `interrupted: true` и `sentAt` — время самой ранней ушедшей части: сама запись создана на старте, и возраст сообщения в оповещении «MAX не разрешил удалить» считается по `sentAt`.
  - **задание** (M29) — `job:<im.message_id>` со `status='in_progress'` на время передачи, с именами файлов в `payload_meta` для оповещения после рестарта; снимается по завершении. Повтор события в это время → `duplicate-in-progress`.
- **Статус доставки** несёт все `maxMids`: Б24 возвращает их в событиях правки и удаления.
- **Удаление** сообщения из нескольких файлов стирает в MAX все его сообщения: id из события + `maxMids` из записи ([Message Deletion](message-deletion.md)). **Правка** меняет подпись на первом.
